# 一台 1GB 内存的白牌电视,还能救:STV920B42 深度精简实录

> 基于个人设备实测。设备为白牌组装机(无 SN/GDID 烧录),方案和固件对同款/同主板机器可直接参考;其他机器请先体检再动手,风险自负。

## 这台机器

| 项目 | 值 |
|---|---|
| 整机 | 荣兴王牌 STV920B42(白牌电视,纯组装机) |
| 主板 | TP.ATM60.PB801A(Amlogic 方案,双核 Cortex-A53 @1.2GHz) |
| 系统 | Android 5.1.1(userdebug 构建类型——这是全文的钥匙) |
| 内存/存储 | 1GB / 8GB |
| 固件 | XD_STV920B42_LightOS_1G_8GB_V20240621 |
| 出厂桌面 | 当贝 LightOS 2.7.0 |
| 面板 | 21.5 寸 1080p LVDS(屏参 M215HGE) |

出厂状态:当贝桌面 81MB 常驻(内嵌 TalkingData 统计 SDK)+ 广告素材下载服务常驻 + 语音双服务常驻。症状:卡顿、界面文字发糊。

## 进入 ADB

这台机器开 ADB 的方法:遥控器**信号源键 → 输入 2 5 8 0 → 工厂菜单 → 常用选项 → ADB 模式**(实测不用重启,立即开放 5555)。

两个要点:

1. **userdebug 构建支持 `adb root`**(重启后失效,需时重做)。这让 system UID 的预装包也能 `pm disable-user`,普通 user 固件做不到。
2. **安全警告**:本机 `ro.adb.secure` 为空 = 免认证,同一网段任何设备都能拿到 shell(配合 adb root 即 root)。**用完就关**,入口就在上面那个工厂菜单。

## 先体检,再动手

动手前的体检结论值得单独一节,因为它决定了整个方向:

| 检查项 | 结果 | 判断 |
|---|---|---|
| MemAvailable | 734MB / 总 975MB | **不缺内存** |
| /data 剩余 | 4.8GB | **不缺存储** |
| 动画缩放 | 已是 0 | 不是动画拖累 |
| 常驻大户 | 桌面 81MB、广告下载 15MB、语音 14+4MB | **重桌面 + 常驻服务叠加弱 SoC** |

结论:卡顿不是「内存不够」也不是「存储满了」,而是双核 A53 扛着重桌面和一堆常驻广告/统计服务。定性对了,下面每一刀才有依据。

## 三轮精简(全程可逆)

**可逆性阶梯**(从上往下风险递增,尽量停在上层):
disable-user > pm clear / uninstall(有备份)> APK 改名 .bak > 删文件(仅单文件、md5 与备份逐字节一致后才删)。

| 轮次 | 操作 | 方式 |
|---|---|---|
| 一 | 禁用广告下载服务、老化测试、自动测试、浏览器、音乐、相册、录音机、语音双件、当贝桌面,共 10 包 | root 后 pm disable-user |
| 一 | 换轻量桌面 Aerial Lite(934KB) | 注意 minSdk:本机 API 22,凡是 minSdk 24/26 的 launcher 都装不上 |
| 二 | 追加禁用当贝助手、当贝市场、工厂测试、BLE 示例、本地播放器,共 5 包 | 同上;前两个后来卸载(APK 已备份 PC 并 md5 核对) |
| 三 | pm clear 桌面数据(96MB→4KB)、卸载助手+市场、关屏保 | /data 释放 187MB+10MB |

**结果:**

| 指标 | 改造前 | 改造后 |
|---|---|---|
| MemFree | 227MB | 512MB(重启峰值,日常回落 ~430MB 属正常) |
| MemAvailable | 734MB | 775MB |
| 桌面内存占用 | 81MB | 32MB |
| 冷启动(开机到可用) | 19.0s | **16.8s(−2.1s)** |
| /data 已用 | 660MB | 464MB |

冷启动提速的归因:PMS 包扫描 3.45→2.30s(卸载+清数据+改名减少扫描量),启动窗口 3.97→2.55s(轻桌面、无广告/语音服务抢资源);固件层 ~4.4s 纹丝不动——底子就这样了。

## 最硬的骨头:禁不掉的语音进程

`pm disable-user` 之后进程还在,`kill` 之后 6 秒换个 PID 复活,`am force-stop` 完全无效——这台机器的语音双件(第三方语音 SDK,uid 1000 + manifest 级 `persistent`)被 ActivityManagerService 自动拉活,**disable 的任何状态都管不住 persistent 进程**。

唯一温和解:**/system 里的 APK 改名 `.apk.bak`**(PMS 扫描不到即不注册),同目录 `lib/` 保留,这样「改回名字重启」就完整恢复。改名前 APK 备份到 PC 并核对 md5。重启后进程消失。

附带一条容易踩的坑:`dumpsys package` 里 `enabled=0` 是 **DEFAULT(启用)**,禁用是 2/3——别看到 0 以为禁掉了。

## 三个死路(省得你试)

1. **UI 分辨率锁死 720p**:面板是 1080p,但 Android 界面被 `const.window.w/h` 锁在 720p(由 systemcontrol 守护进程开机写死,SurfaceFlinger 只读)。`wm size 1920x1080 + wm density 240` 实测完全无效——帧缓冲和真实渲染纹丝不动。这是 1GB 内存档的故意阉割,动它等于动固件二进制。视频走独立 video plane 不受影响,所以只是界面糊、视频不糊。
2. **开机进信号源**:Amlogic 框架写死直接拉起电视输入,改 settings 无效;按一次 Home 键进桌面,凑合用。
3. **换开机 logo 提速**:把 AML_RES! 格式逆向了(头校验 = NOT(crc32(img[4:used_size])),bootup 资源是 gzip 压缩的 1920×1080 BMP),本地打包器能逐字节复现原厂文件——结果证明开屏图和开机速度无关。这条纯粹是兴趣,顺便证明 logo 分区与 bootloader 分离,不是启动链。

## 附赠调查:B 站 TV 版切视频为什么卡

精简完成后实际体验:整体流畅稳定,**唯独切换视频时明显卡顿**。为此做了三方分观测的仪器化复现:一人远程驾驶真实切换,一人 60 轮×3 秒系统高频采样,一人对 logcat 逐帧对齐。

**先说弯路**(值得引以为戒):第一版归因是「GC 风暴」——logcat 里 35 秒 24 次 GC 加 59 帧掉帧,和切换时间窗「严丝合缝」。分桶直方图一画:那些 GC/掉帧**全部落在应用冷启动阶段**,和切换窗口只是时间重叠。撤回。

**定版数据**:5 次仪器化切换,主线程**零掉帧**,GC 全部是 concurrent 后台型(单次暂停最长 71ms);系统侧 load 峰值 5.97~7.95(双核满载 2.0 的 3~4 倍超订,来自后台拆建播放器+P2P 换源),eMMC 写峰值仅 535KB/3s(排除 IO),zram 全程 0(排除换页),3 分钟连续切换温度爬升 12°C(连切是热负荷)。

**结论**:切换时的「卡」是**加载延迟**——旧播放器整个拆掉、再和新视频源建流,黑屏/加载圈 1~2 秒。UI 从来没有冻结,这是应用设计 × 硬件等级的固有成本,系统侧没有安全的优化杠杆。

真正痛的操作排序:**冷启动**(主线程掉 112/121 帧 + 22 秒开屏广告)≫ **快速连按**(被翻页动画吞键,连按两下只生效一下)≫ **正常切换**(等 1~2 秒而已)。

用户侧缓解:别杀应用(后台常驻,免掉最痛的冷启动)、切换慢一点、降默认清晰度、关弹幕。

## 经验清单

1. **先体检定性再动手**:内存/存储/IO/温度逐项排除,否则每刀都赌。
2. **可逆性阶梯**:disable > clear/uninstall > 改名 > 删文件;删任何文件前 md5 备份到 PC。
3. **persistent + uid 1000 = 改名 .bak 唯一解**,lib/ 目录保留。
4. **每轮改动后重启验证**,对账禁用包数量零回退。
5. **警惕窗口重叠错觉**:两个现象时间上重合 ≠ 因果;分桶直方图是最便宜的拆穿工具。
6. **区分两类「卡」**:掉帧(UI 冻结)和加载延迟(等)——处理方式完全不同。
7. **恢复出厂 = 全部推倒**(禁用状态存 packages.xml,清空即复活),白牌机没有官方固件兜底,更别刷机。
8. ADB 免认证的机器,**用完就关**。
